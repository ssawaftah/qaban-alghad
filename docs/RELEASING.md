# بناء ونشر الإصدارات

## الحالة الحالية

هذا المستودع يجهز بناءً آليًا وحزمة خالية من الأسرار. مهمة verify.yml تبني وتختبر ثم تنشر إصدار GitHub بعد نجاح مهمتي Windows وHTTP عند push إلى main. يوجد Updater مستقل ويقرأ التطبيق أحدث إصدار رسمي عبر API؛ لا يعتمد على رابط Artifact مؤقت.

## سياسة الأرقام

`VERSION` يحتوي رقمًا ثلاثيًا، مثل0.9.3. حدّث معه AssemblyVersion وAssemblyFileVersion في `Properties/AssemblyInfo.cs`، وسجل التغيير في CHANGELOG.md. سكربت التغليف يرفض اختلاف أول ثلاثة أجزاء من إصدار EXE عن VERSION.

## الإجراء المرجعي

1. أنشئ فرعًا للتغيير وراجع اختبارات Windows وHTTP.
2. اختبر الحزمة على Windows وقراءة القبان قبل اعتماد إصدار إنتاجي.
3. حدّث الإصدار وسجل التغيير ووثائق السلوك المتغير.
4. شغّل `scripts/package.ps1`؛ يعيد البناء والاختبارات ثم يخرج ZIP في dist.
5. افحص محتويات ZIP: EXE وconfig وأيقونة وStart.cmd ودليل المستخدم وSHA256.json فقط.
6. أنشئ Tag باسم `v<version>` وإصدار GitHub بعد اجتياز المراجعة. لا يكفي تعديل source وحده.
7. ارفع الحزمة الخالية من الأسرار، وأرفق ملاحظات التغيير وحدود التحقق.
8. لا تنشر بيانًا منفصلاً؛ يعتمد العميل على بيانات Release asset وdigest التي توفرها GitHub.

## التغليف الخاص

يجب أن تبقى تهيئة الجهاز خارج الإصدار العام. إذا احتجت حزمة خاصة لمرة واحدة، يتم تسليم ملف التهيئة بقناة خاصة معروفة وإضافته محليًا. لا ترفع `Returns.setup.json` إلى Release عام أو workflow artifact. لا يمكن إخفاء سر إنتاجي بوضعه في مستودع خاص ثم نسخه إلى حزمة عامة.

## الرجوع

حاليًا الرجوع يدوي بتشغيل الحزمة السابقة بعد إغلاق الجديدة، مع الحفاظ على AppData وعدم حذف الإعدادات. نسخة0.9.2 هي آخر نسخة أكد المستخدم عملها قبل هذا النقل. توجد معاملة تثبيت ونسخة old وjournal ورجوع تلقائي عند فشل بدء التشغيل؛ راجع ONLINE_UPDATES.md.

## ما الذي تحقق محليًا؟

البنية الجديدة اجتازت195 تحققًا باستخدام Mono، وشملت اختبارات تفحص EXE التطبيق المشار إليه من مشروع الاختبارات. نجحت مهمة Windows الأصلية للبناء والاختبار والتغليف، ومهمة HTTP integration على GitHub Actions في التشغيل 42853454763. فحص الواجهة والمنفذ الفعلي لهذا الإصدار المرشح ما زال مطلوبًا قبل اعتماده ميدانيًا.
