# خطة ترقية .NET مع الحفاظ على التشغيل

الحالة: خطة جاهزة للتنفيذ بعد جرد أجهزة القبان. لا يتغير الاستهداف الحالي `.NET Framework 4.5.1` في هذا التعديل. لم يحدد المالك أقدم Windows مطلوب بعد، وسيزوّد إصدار `winver` ورقم البناء من الأجهزة الفعلية. وجود استهداف 4.5.1 لا يعني أن الجهاز يشغّل هذه النسخة تحديدًا؛ إصدارات Framework الأحدث قد تشغّل التطبيق نفسه.

## المعلومات المطلوبة من كل جهاز

- إصدار Windows ونسخته ورقم البناء من `winver`، ومعمارية النظام x86/x64.
- نسخة .NET Framework المثبتة (قيمة Release في مفتاح NDP v4 Full)، وصلاحية تثبيت متطلبات التشغيل؛ لا تجمع معلومات اعتماد أو رموز ربط.
- نوع محول USB/Serial وإصدار تعريفه، والمنفذ، وإعداداته، وصيغ الإطارات بعد إزالة أي بيانات خاصة.
- سياسات التحديث والشبكة والشهادات، وطريقة العمل دون اتصال، وصلاحية الكتابة بمجلد البرنامج.

## المسارات المرشحة

| المسار | متطلبات التشغيل والتحقق | أثر التغيير |
| --- | --- | --- |
| البقاء على الاستهداف الحالي مؤقتًا | الحفاظ على نسخة Framework المثبتة والتأكد من سلامة Windows ودعمه | أقل تغيير أثناء جمع الجرد؛ ليس ادعاء بأن Framework 4.5.1 ما زال مدعومًا |
| .NET Framework 4.8 أو 4.8.1 | اختيار النسخة التي تدعم جميع إصدارات Windows الموثقة وفق قوائم Microsoft، ثم التحقق من تثبيتها قبل الترقية | خطوة انتقالية قريبة من WinForms الحالي وDPAPI وواجهات JSON الحالية |
| .NET حديث طويل الدعم، مثل .NET 10 LTS | مراجعة نظام Windows المدعوم ومعماريته، واختيار Desktop Runtime أو نشر مستقل؛ التحقق من دورة الدعم وقت الاعتماد | يتطلب معالجة System.Web.Extensions ونقل HTTP والتغليف وعقد المحدّث؛ ينفذ في فرع مستقل |

مراجع المتطلبات: [دليل تثبيت Framework](https://learn.microsoft.com/dotnet/framework/install/)، [دعم أنظمة تشغيل .NET](https://github.com/dotnet/core/tree/main/release-notes)، [دورة دعم .NET](https://dotnet.microsoft.com/platform/support/policy/dotnet-core). لا تعتمد حد Windows أدنى من التخمين أو من اسم الجهاز.

## ثوابت لا تتغير

تبقى مساحة الأسماء ومجلد AppData وmutex وأسماء حقول JSON وentropy وDPAPI/CurrentUser كما هي. تبقى القناتان مستقلتين، ويرسل كل منهما أحدث قراءة مستقرة حديثة دوريًا حتى مع ثبات الوزن. الأساسي ينهي المحاولة بعد كتابة الجسم، والثانية تتحقق من إقرار مطابق. لا يتغير COM أو DTR/RTS أو Handshake أو مهلة الحداثة تلقائيًا.

## مراحل التنفيذ

1. اعتماد مصفوفة أجهزة وأنظمة تشغيل وإصدارات Framework الفعلية. تثبيت خط أساس من الحزمة الحالية وقياس زمن وصول القراءة وتواتر الإرسال واستهلاك الذاكرة على جهاز اختبار.
2. اختيار الهدف في تغيير مستقل. تحديث الاستهداف والمراجع وسكربت Windows والاختبارات فقط. تبقى معالجة الإطارات وعقود الوجهتين مغطاة بنفس fixtures والطلبات المحلية.
3. التحقق من JSON: الوزن الأساسي نص، ووزن القناة الثانية رقم، وثقافة النظام لا تغيّر الفاصلة، والصفر والسالب والكسور تبقى صحيحة. لا يستبدل System.Web.Extensions بمكتبة أخرى دون اختبارات توافق.
4. التحقق من الترقية: مكتبات .NET الحديثة قد تحتاج ملفات runtimeconfig/deps/DLL إضافية، أو حزمة مستقلة تتجاوز 32MiB. يجب تعديل قائمة الملفات المسموح بها وحد الحجم وعقد الاستعادة واختبارها صراحة. يمكن أن يلزم إصدار تمهيدي بالمحدّث القديم قبل نقل التطبيق. لا تُخفّف قواعد ZIP أو البصمة بصورة عامة.
5. تجهيز متطلبات التشغيل خارج مسار قياس الأوزان. اكتشاف غياب Runtime قبل إيقاف القبان؛ لا تثبيت تلقائيًا بصلاحيات مدير من داخل التطبيق. للحزم غير المتصلة، توثيق مثبت Microsoft الموثوق والتحقق منه.
6. اختبار Windows أصلي لكل نظام ومعمارية معتمدين. تشغيل الفحوص المحلية ثم الترقية من آخر حزمة ميدانية والاستعادة عند فشل البدء. اختبار DPAPI بنفس حساب Windows باستخدام رموز اصطناعية فقط.
7. تجربة على جهاز احتياطي دون إرسال أوزان اصطناعية للإنتاج: فصل المحول وإعادته، صمت المنفذ، إعادة التشغيل، انقطاع الشبكة، اختلاف ساعة النظام، وثبات الوزن لفترات طويلة.
8. طرح تدريجي على جهاز واحد في وقت متفق عليه، بحزمة سابقة محفوظة ونسخة إعدادات محلية. بعد ظهور الواجهة يضغط المشغّل تشغيل ثم يطابق قراءة حقيقية وحالة الموقع. لا توصف إشارة جاهزية الواجهة بأنها تحقق من القبان أو الحفظ لدى الخادم.

## بوابة القبول والرجوع

لا اعتماد للترقية قبل نجاح مصفوفة Windows، وتطابق البروتوكول والطلبات، وبقاء إعدادات المنفذ والوجهة والرموز دون تغيير، ونجاح rollback الحقيقي. قياسات التأخير لا تتراجع عن حدود متفق عليها مقارنة بخط الأساس. إذا فشل Runtime أو التعريف أو التحديث، يرجع الجهاز للحزمة السابقة دون ترحيل غير قابل للعكس لملف الإعدادات.

## التوقيع

أضيف مسار اختياري `scripts/sign.ps1`؛ لا توجد شهادة مرفقة أو مفاتيح مولدة. عندما تتوفر شهادة موثوقة في مخزن حساب مشغّل البناء وWindows SDK، ينفذ:

```powershell
.\scripts\package.ps1 -CertificateThumbprint '<thumbprint>'
```

التوقيع يحدث بعد البناء وقبل حساب بصمات الحزمة؛ يتم التحقق من هوية الموقّع والتوقيع. استيراد شهادة على مشغّل GitHub Actions مؤقت مسؤولية مالك الشهادة من مخزن أسرار آمن، مع إزالة الشهادة عند انتهاء المهمة وعدم طباعة كلمة المرور. لا تشغّل مهمة تحمل مفاتيح على طلبات مساهمة غير موثوقة. المسار الافتراضي يظل غير موقّع؛ SHA-256 وHTTPS لا يصبحان توقيعًا مستقلًا. فرض توقيع مثبت داخل عميل التحديث تغيير ثقة مستقل يتطلب خطة تدوير للشهادات واختبارات استعادة.
