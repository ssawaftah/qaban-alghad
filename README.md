# قبان الغد | Qaban AlGhad

تطبيق Windows يقرأ الوزن من جهاز القبان عبر منفذ تسلسلي، ويعرض أحدث قراءة مستقرة بواجهة عربية، ويرسلها إلى وجهتين مستقلتين عبر HTTPS. المستودع يضم تطبيق سطح المكتب وأداة التحديث واختباراتهما. نظام الشركة وموقع إدارة المرتجعات تطبيقان منفصلان.

- **المطور:** Abdelrahman Sawaftah
- **المستودع الرسمي:** [ssawaftah/qaban-alghad](https://github.com/ssawaftah/qaban-alghad)
- **نسخة المصدر:** ملف [VERSION](VERSION). يظهر الرقم في البرنامج من إصدار التجميعة في [AssemblyInfo.cs](src/QabanAlGhad/Properties/AssemblyInfo.cs).
- **نسخة المستخدم:** حزمة Windows في [أحدث إصدار منشور](https://github.com/ssawaftah/qaban-alghad/releases/latest). قد يتقدم فرع `main` بالتوثيق أو الاختبارات على الالتزام الذي يشير إليه الإصدار المنشور.

## ابدأ هنا عند تطوير المشروع في Codex

1. اقرأ [AGENTS.md](AGENTS.md) وملف `README.md` هذا. استخدم [خريطة الأكواد](docs/CODE_MAP.md) لتحديد نقطة الدخول، ثم اقرأ الكود والاختبارات الخاصة بالميزة.
2. ابدأ من فرع `main` في المستودع الرسمي. افحص `git status` وحافظ على تغييرات المستخدم الموجودة في مساحة العمل. سجّل الالتزام الذي راجعته عند التحقيق في مشكلة مرتبطة بإصدار.
3. إذا اختلف مستند قديم مع الكود أو اختبارات النسخة الحالية، اتبع التنفيذ الحالي وتحقق من السلوك المطلوب قبل تعديل أي عقد. بعض المستندات تسجل مراحل سابقة من المشروع.
4. نفّذ التغيير عبر المسار الفعلي المستخدم داخل التطبيق. حافظ على القراءة والإرسال والإعدادات كما يتوقعها المستخدم في المناطق التي لا تشملها المهمة.
5. شغّل الاختبارات المناسبة وحدد بوضوح ما تحقق محليًا، وما تحقق على Windows، وما يتطلب جهاز القبان الحقيقي. استخدم عناوين محلية وبيانات اصطناعية عند اختبار النقل.
6. عند طلب إصدار جديد، حدّث رقم الإصدار والملحوظات وتحقق من نجاح GitHub Actions ومن الحزمة المنشورة. تغيير التوثيق وحده يبقى على رقم الإصدار الحالي.

## تشغيل البرنامج على Windows

1. نزّل `QabanAlGhad-<version>.zip` من صفحة الإصدار، وفكّه كاملًا إلى مجلد يملك المستخدم صلاحية الكتابة فيه حتى يعمل التحديث من داخل التطبيق.
2. افتح `QabanAlGhad.exe`. يسمح التطبيق بنسخة واحدة عبر mutex باسم `WeighbridgeBridge.SingleInstance`. أغلق قارئ القبان القديم قبل فتح المنفذ نفسه.
3. افتح **الإعدادات** لتحديد منفذ COM وإعداداته وعنوان النظام الأساسي ورقم الشركة. قارنها بتهيئة جهاز الشركة الفعلية قبل تغييرها.
4. اضغط **تشغيل** لبدء القراءة والإرسال، أو **إيقاف** لإيقافهما. يعرض تبويب **السجل** القراءات والأحداث، وتعرض أداة **فحص الاتصال** المنافذ المتاحة وآخر قراءة وإرسال. يمكن نسخ تقرير تشخيص أو حفظه إلى ملف نصي.
5. اضغط **!** داخل الدائرة أعلى يسار النافذة لفتح معلومات الإصدار. اختر **التحقق من التحديثات**، ثم **يوجد تحديث** عند توفره، وأكد التثبيت. بعد إعادة الفتح، اضغط **تشغيل** لاستئناف القراءة. يظهر رقم النسخة واسم المطور أسفل النافذة.

## مسار الوزن من الجهاز إلى الوجهتين

1. **فتح المنفذ.** يبدأ `MainForm.Weighing.cs` عامل قراءة واحدًا في الخلفية. الإعداد الافتراضي `COM6 / 9600 / 8 / None / 1`، والمنفذ قابل للتغيير. يتجاهل المجمّع ذيل أول إطار ناقص عند بدء القراءة وسط بث الميزان. يعيد العامل فتح المنفذ عند فشل الاتصال أو انقطاع البث، بفاصل يتدرج من ثانية إلى 15 ثانية. حد صمت المنفذ هو الأكبر بين 5 ثوانٍ وضعف مهلة الحداثة.
2. **تجميع الإطارات.** يقبل `Frames.Push` أجزاء غير مكتملة أو عدة إطارات في دفعة واحدة. يستخدم CR/LF للفصل، ويضع حدًا قدره 16384 حرفًا للإطار، ثم يستأنف عند الفاصل التالي. إذا وصل إطار غير صالح بعد إطار صالح في الدفعة نفسها، يعكس الناتج حالة الإطار الأحدث.
3. **تفسير الوزن.** يقبل `Protocol.Parse` الصيغ المستقرة المدعومة من `ST,GS` و`ST,NT` و`1,ST`. يحافظ على الصفر والسالب والكسور، ويرفض `US` والوحدات الصريحة غير المدعومة. بعض الصيغ القديمة ترسل الرقم دون حقل وحدة صريح، وتظل مقبولة لكونها مستخدمة في الربط الحالي. تُفسّر الأرقام وتُكتب JSON دون التأثر بلغة Windows.
4. **التوقيت والواجهة.** يسلّم العامل أحدث إطار إلى الواجهة عبر خانة مشتركة محمية بقفل. يستخرج مؤقت WinForms الحالة دوريًا ويحدّث العرض. عمر العينة يحسب بساعة رتيبة من وصول الإطار، ووقت `sampledAt` هو UTC عند وصوله. تكرار الوزن نفسه في إطار جديد يجدّد العينة.
5. **الإرسال.** تستدعي الواجهة `Pump` لكل وجهة. لكل وجهة طلب جاري وجدولة مستقلان. عند توفر قراءة صالحة وحديثة، تبدأ محاولة بفاصل اسمي ثانية واحدة حتى إذا ثبت الوزن. تؤثر مهلة الطلب والتراجع بعد الأعطال في الفاصل الفعلي. كل محاولة تأخذ أحدث عينة متاحة، ولا يعاد إرسال طابور من الأوزان القديمة.
6. **الاسترداد والحالة.** مهلة حداثة القراءة 3000ms افتراضيًا، ويمكن ضبطها من 1000 إلى 30000ms. مهلة الطلب مرتبطة بما تبقى من الحداثة وبحد أقصى 8000ms. يزيد فاصل المحاولة عند فشل الاتصال أو الكتابة ثم يعود إلى الفاصل المعتاد عند نجاح الإرسال. يعرض المؤشر حالة القراءة والكتابة المحلية. أخضر **يعمل ويرسل** يعني وجود قراءة حديثة وكتابة حديثة للقناة الأساسية.

### عقود الإرسال

| العنصر | نظام الشركة الأساسي | الوجهة الثانية للمرتجعات |
| --- | --- | --- |
| الوجهة | عنوان `Settings.Endpoint` المحفوظ محليًا | عنوان `ReturnsEndpoint` في إعدادات الجهاز |
| الطلب | `POST` مع JSON، والمصادقة Bearer عند تهيئتها | `POST` مع JSON ورمز Bearer مطلوب |
| مثال جسم الطلب | `{"company_id":"1","weight_scale":"-20"}` | `{"weightKg":-20,"sampledAt":"2026-11-10T10:00:00.0000000Z"}` |
| نوع الوزن | نص JSON | رقم JSON |
| الاستجابة | تنتهي المحاولة بعد كتابة الجسم؛ لا تنتظر رؤوس HTTP أو جسم الرد | ينتظر إقرارًا يتضمن `accepted:true` ووزنًا مطابقًا، ويحترم `Retry-After` الرقمي |

كتابة الطلب في القناة الأساسية لا تؤكد حفظ الوزن لدى الموقع. لا تعد إضافة انتظار الرد إلى هذه القناة إصلاحًا عامًا لأخطاء الإرسال، لأن الموقع قد يستقبل البيانات ولا يرد. يبقى رصد خطأ TLS أو انتهاء المهلة قبل اكتمال الكتابة منفصلًا عن حالة القراءة. كلا المسارين يستخدم HTTPS في الإنتاج، ويمنع تحويلات HTTP التلقائية. وضع HTTP المحلي مخصص للاختبارات.

قيمة عنوان الشركة الافتراضية في المصدر ليست مرجع عنوان جهاز يعمل في الميدان. احتفظ بعنوان الشركة المحفوظ وإعداد المنفذ عند الترقية أو إصلاح التهيئة. راجع [عقود الربط](docs/API_CONTRACTS.md) لصيغة البيانات، واتبع السلوك الموصوف هنا عند تعارض تفاصيل انتظار الرد مع شرح تاريخي.

## الإعدادات والملفات المحلية

- استخدم `%LOCALAPPDATA%\WeighbridgeBridge` على حساب Windows الذي يشغّل البرنامج. يوجد `settings.json` هناك، و`settings.json.bak` بعد حفظ نسخة سابقة صالحة. يكتب التطبيق إلى ملف مؤقت ثم يستبدل الملف. يحاول قراءة النسخة الاحتياطية عند التلف، ويطلب إصلاح الإعدادات إذا تعذرت قراءة النسختين.
- حقول JSON مثل `Port` و`Endpoint` و`Company` و`Freshness` جزء من توافق الترقيات. حافظ على الأسماء والقيم والمعاني المستخدمة في النسخ المثبتة. عند الحاجة إلى تغيير مخطط، جهّز ترحيلًا واختبره مع ملف من النسخة السابقة بعد إزالة البيانات الخاصة.
- الرموز محمية باستخدام Windows DPAPI بنطاق `CurrentUser`. نسخ ملف إعدادات إلى حساب أو جهاز آخر لا يضمن إمكان فك التشفير. حافظ على قيمة entropy الثابتة في `LocalSecrets` عند إعادة تنظيم الكود.
- يستورد `Bootstrap.Import` ملف التهيئة الخاص `Returns.setup.json` من مجلد التطبيق إن وُجد، ويحفظ الرمز مشفرًا ثم يحذف ملف التهيئة عند نجاح الحفظ. قفل الإعدادات يقيّد الوصول من الواجهة، وتبقى صلاحيات حساب Windows ومجلداته مهمة لحماية التهيئة المحلية.
- السجلات `readings.log` و`bridge.log` و`background.log` تُكتب من عامل خلفي بطابور محدود. تتوفر سجلات مدوّرة، ويعرض فحص الاتصال عدادات أخطاء الكتابة والأحداث التي لم تُحفظ. تقارير الدعم تستبعد الرموز وعناوين الربط والإطار الخام.
- الأمثلة في [examples](examples/) معدّة للشرح. احتفظ بالإعدادات الفعلية والرموز والسجلات والنسخ الاحتياطية والحزم المهيأة خارج GitHub وخارج حزمة التوزيع.

## البناء والاختبار

التطبيق **WinForms** ويستهدف **.NET Framework 4.5.1** حاليًا. البناء على Windows يستخدم مترجم .NET Framework في النظام، ويمكن فتح [QabanAlGhad.sln](QabanAlGhad.sln) في Visual Studio عند توفر حزمة الاستهداف. راعِ توافق المترجم وواجهات API عند إدخال صياغة C# أو مكتبات جديدة. إذا أضفت ملف C#، راجع قوائم `Compile Include` في ملفات `.csproj` إلى جانب سكربتات البناء.

### Windows

نفّذ من جذر المستودع:

```powershell
.\scripts\build.ps1
.\out\QabanAlGhad.Tests.exe --integration-test
.\scripts\package.ps1
```

- `build.ps1` يبني التطبيق والمحدّث والاختبارات ويشغّل فحوص البروتوكول والتوافق والقناتين والواجهة ودورة التحديث والاستعادة. استخدم `-SkipTests` فقط إذا كانت المهمة تحتاج بناءً دون تشغيل الفحوص.
- `--integration-test` يختبر HTTP على loopback. قد يتطلب `HttpListener` صلاحية URL ACL بحسب تهيئة Windows.
- `package.ps1` يبني الحزمة العامة في `dist/` من قائمة ملفات محددة. يكتب نواتج البناء في `out/`. كلا المجلدين خارج ملفات المصدر المتتبعة.

### Linux أو Mono

```bash
bash scripts/test-mono.sh
```

يدعم السكربت متغير `QABAN_MONO_ROOT` لحزمة Mono محلية عند الحاجة. يشغّل فحوص المنطق ونقل loopback. تحقق Windows هو مرجع الواجهة والحزمة والترقية، ويظل اختبار المنفذ والموقع الفعليين منفصلًا على جهاز الشركة.

## نشر إصدار وتثبيته

1. حدّث [VERSION](VERSION) و`AssemblyVersion` و`AssemblyFileVersion` في [AssemblyInfo.cs](src/QabanAlGhad/Properties/AssemblyInfo.cs) معًا. رقم النسخة في الواجهة يُقرأ من التجميعة، فلا تكتبه يدويًا في الواجهة.
2. أضف التغيير إلى [CHANGELOG.md](CHANGELOG.md) واكتب [ملحوظات الإصدار](docs/RELEASE_NOTES.md) الخاصة بالحزمة التي ستُنشر.
3. راجع GitHub Actions. يبني فحص Windows الحزمة، ويستخدم فحص HTTP نفس ملفات Windows المبنية. بعد نجاحهما، ينشر سير العمل إصدار `v<version>` من دفعة إلى `main` ويحمّل `QabanAlGhad-<version>.zip`. إصدار منشور بالرقم نفسه لا يستبدله سير العمل.
4. تحقق من صفحة الإصدار والحزمة ومن نتيجة فحص الترقية عبر الإنترنت. يختبر هذا الفحص عميل التحديث مع حزمة سابقة منشورة. يظهر الالتزام المثبت في صفحة الإصدار، وقد يختلف عن رأس `main` بعد تغييرات التوثيق.
5. عند التحديث من داخل التطبيق، يتحقق العميل من إصدار GitHub وبصمة SHA‑256 واسم الحزمة وحجمها. تُستخرج الملفات المسموح بها إلى مجلد تجهيز. بعد تأكيد المستخدم، يوقف التطبيق القراءة والإرسال ويسلّم التثبيت إلى أداة منفصلة. تحفظ الأداة نسخة احتياطية، وتستبدل ملفات التشغيل الأربعة، وتنتظر إشارة جاهزية التطبيق أو تستعيد النسخة السابقة. تبقى الإعدادات في مجلد بيانات المستخدم.
6. تعتمد الثقة في الحزمة حاليًا على مستودع GitHub الرسمي وHTTPS والبصمة التي يوفرها GitHub. سجّل أي تغيير في نموذج التوقيع أو الاستعادة في [دليل التحديث عبر الإنترنت](docs/ONLINE_UPDATES.md).

| الموقع يعرض وزنًا قديمًا مع مؤشر أخضر | طابق وقت قراءة جديدة على القبان ووقت تغيرها في الموقع. المؤشر يؤكد الكتابة المحلية؛ تأكيد الاستلام يُفحص لدى الموقع |
| «تعذر التحقق» عند طلب التحديث | تحقق من وصول جهاز Windows إلى GitHub ومن الإصدار المنشور. اقرأ سجل التحديث قبل تغيير الثقة بالشهادات أو الرابط |
| تعذر فتح البرنامج بعد تحديث | راجع سجلات `update-error.log` و`update-status.log` في مجلد التطبيق وسجل الاستعادة. احتفظ بملفات التجهيز والنسخة السابقة حتى يتضح سبب العطل |
